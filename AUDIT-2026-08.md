# PVM Code Audit — August 2026

**Audit Scope:** Full repository — `schemas/v1/`, `specs/`, `examples/`  
**Audit Date:** 2026-08-02  
**Status:** Findings publicly disclosed; all critical issues addressed

---

## Executive Summary

PVM (PayPack Value Metadata Specification) is a well-designed but early-stage specification for AI agent payment trust assessment. The core insight — x402/AP2 solve "how to pay," PVM solves "whether the payment is worth making" — is directionally correct and fills a genuine gap in the AI payments ecosystem.

This audit identified three structural issues. All three have been resolved as of 2026-08-02.

---

## What PVM Gets Right

| Area | Assessment |
|------|-----------|
| **Direction** | 9/10 — Correctly identifies the "trust gap" above payment protocols |
| **Statistical rigor** | Tukey's fences for fair price ranges, 300-850 credit scoring à la FICO |
| **Schema ↔ SQL consistency** | Price index JSON Schema and SQL DDL fields are 1:1 aligned |

## Identified Issues & Resolutions

### Issue #1: Weight Contradiction (RESOLVED ✅)

**Severity:** 🔴 Critical  
**Location:** `schemas/v1/credit-score.json` vs `schemas/v1/price-index.sql`

**Problem:** `credit-score.json` declared price integrity at 40% weight, while `price-index.sql` line 77 used a 60%/40% split formula. Two authoritative definitions within the same spec were contradictory.

**Resolution:** 
- Updated `price-index.sql` formula to match the Schema: 40% price deviation + 30% user rating + 30% fulfillment rate
- Added alignment statement in `CONTRIBUTING.md`: JSON Schema is authoritative; SQL is reference

---

### Issue #2: Judgment Logic Vacuum (RESOLVED ✅)

**Severity:** 🔴 Critical  
**Location:** `schemas/v1/value-metadata.json` `risk_level` field

**Problem:** `risk_level` had four enum values (LOW/MEDIUM/HIGH/BLOCKED) but no rules for which to assign. `sample_count` had no minimum threshold. `confidence` had no calculation method.

**Resolution:**
- Created `specs/risk-assessment.md` with explicit decision rules for all four risk levels
- Defined `sample_count` minimum threshold (30) and `confidence` calculation formula (sqrt-based with time decay)
- Updated `value-metadata.json` `risk_level` description to reference the rules doc

---

### Issue #3: Core Algorithm Centralization (RESOLVED ✅)

**Severity:** 🟡 High  
**Location:** `trust_score` calculation — previously marked "managed by PayPack Cloud" only

**Problem:** The `trust_score` that determines whether a payment should proceed was a black box. The open-source spec defined data structures but not the decision logic behind the most critical field.

**Resolution:**
- Created `specs/trust-score-methodology.md` with full three-dimensional weighted model (price integrity 40%, fulfillment 30%, user rating 30%)
- Includes Bayesian adjustment for small-sample user ratings, time decay formulas, and the 0-100 → 300-850 mapping
- Strategy: "Verifiable Transparent Trust" — algorithm is open for audit; raw transaction data remains secured to prevent manipulation
- Updated `credit-score.json` and `ai-service-metadata.json` to reference the methodology doc
